# Implementation Plan

## 1. 基盤: モデル種別の型と対応表

- [x] 1.1 モデル種別と新パラメータを表すデータ型を追加する
  - 3 つのモデル種別、complexity の 3 段階、API 形式（deployments / v1）を表す型を定義する
  - quality・background・出力形式の型を、2.5 系の値（xhigh / max / auto、opaque、webp）まで広げる
  - 生成・編集のパラメータにモデル種別（既定 gpt-image-2）と complexity（既定は未指定）を、編集のパラメータに markup（既定は未指定）を、Azure の設定に API 形式（既定 deployments）とトークンのスコープ（既定は従来の値）を追加する
  - 完了条件: 既存のコードがそのまま動き（既存の 118 件のテストが成功し）、新しいフィールドが既定値つきでインスタンス化できる
  - _Requirements: 1.1, 6.1, 7.1, 9.5, 11.1_

- [x] 1.2 モデル種別ごとの対応表と機能フラグを作る
  - モデル種別ごとに、使える quality・background・出力形式、宣言上対応する機能（complexity / markup / webp）、experimental とみなす総ピクセル数、生成・編集のタイムアウト、デプロイ名の環境変数名を宣言する
  - 機能フラグの初期値を、complexity と markup は有効、WebP は無効にする。環境変数では切り替えられないようにする
  - 「宣言上の対応」と「機能フラグ」の両方を満たすときだけ機能が使える、という判定と、透過・圧縮に対応する出力形式の集合を返す判定を用意する
  - gpt-image-2 の対応表は既存の許可値・タイムアウト（120 秒・180 秒）と同じにし、2.5 系は 300 秒にする
  - 完了条件: 単体テストで、モデルごとの許可値、フラグの切り替え（monkeypatch）による機能判定の変化、gpt-image-2 の表が既存の定数と一致すること、デプロイ名の環境変数名の生成規則を確認できる
  - _Requirements: 1.1, 2.1, 3.1, 3.2, 4.1, 4.2, 5.2, 6.6, 7.7, 8.1, 10.1, 10.3_

## 2. コア: 寸法の読み取り・設定・認証・検証・送信

- [x] 2.1 (P) 画像ファイルの寸法をヘッダから読み取れるようにする
  - 標準ライブラリだけで、PNG・JPEG・WebP（VP8 / VP8L / VP8X）のヘッダから幅と高さを読む
  - JPEG では EXIF の向き（5〜8）に応じて幅と高さを入れ替える
  - 形式を判定できない、またはヘッダが壊れている場合は例外にせず「不明」を返し、ファイル全体は読み込まない
  - 完了条件: 単体テストで、各形式（EXIF で向きが入れ替わる JPEG を含む）の寸法が正しく読め、壊れたファイルや未対応形式で「不明」が返る
  - _Boundary: image_info_
  - _Requirements: 7.6_

- [x] 2.2 (P) モデル種別に応じて呼び出し先のデプロイと API 形式を決める
  - 設定の読み込みでモデル種別を受け取れるようにし（省略時は gpt-image-2）、モデル種別ごとのデプロイ名の環境変数 → 共通の `AZURE_OPENAI_DEPLOYMENT` の順で探す
  - どちらも未設定なら、両方の環境変数名を含み、値を含まない設定エラーにする
  - API 形式（`AZURE_OPENAI_API_STYLE`）とトークンのスコープ（`AZURE_OPENAI_TOKEN_SCOPE`）を読み、v1 形式で api-version が未設定なら preview を既定にする。不正な API 形式は設定エラーにする
  - デプロイ名からモデル種別を推測しない
  - 完了条件: 単体テストで、モデル種別ごとの環境変数の優先、フォールバック、未設定時のエラー文、API 形式とスコープの既定・上書き・不正値を確認できる。既存の設定テストも成功する
  - _Boundary: config_
  - _Requirements: 1.4, 2.1, 2.2, 2.3, 2.4, 9.5_

- [x] 2.3 (P) Entra ID トークンのスコープを指定できるようにする
  - 認証の解決でトークンのスコープを受け取れるようにし、省略時は従来のスコープを使う
  - Entra ID を優先して API キーにフォールバックする順序や、シークレットを出力しない方針は変えない
  - 完了条件: 単体テストで、指定したスコープでトークンが要求され、省略時は従来のスコープが使われることを確認できる。既存の認証テストも成功する
  - _Boundary: auth_
  - _Requirements: 9.5_

- [x] 2.4 (P) 対応表に基づいて生成・編集のパラメータを検証する
  - quality・background・出力形式を、モデル種別の許可値で検証する。エラー文にはモデル種別の名前と使える値を含める。gpt-image-2 では既存のエラー文を変えない
  - 透過は、モデルの「透過に対応する出力形式」でのみ受け付ける。圧縮の指定は、モデルの「圧縮に対応する出力形式」のときだけ有効にする（それ以外は従来どおり警告して無視する）
  - WebP は、モデルが対応し、かつ機能フラグが有効なときだけ受け付ける
  - complexity は 3 段階の値のみを受け付け、gpt-image-2 では「2.5 系専用」、フラグが無効なら「Azure では現在利用できない」というエラーにする
  - 2.5 系で size が auto 以外のとき、総ピクセル数が 2560x1440（3,686,400）を超えたら、処理を続けたうえで experimental の警告を標準エラー出力に出す。size の制約そのものと、編集の size=auto の扱いは変えない
  - 完了条件: 単体テストで、2.5 系での xhigh・max・auto・opaque の受け付け、gpt-image-2 での拒否、experimental の警告の境界値（3,686,400 ちょうどでは警告しない）、complexity と WebP の 3 つの状態（モデル非対応 / フラグ無効 / 有効）を確認できる。既存の検証テストも成功する
  - _Boundary: validation_
  - _Requirements: 3.1, 3.2, 3.3, 4.1, 4.2, 4.3, 4.4, 5.1, 5.2, 5.3, 5.4, 6.4, 6.5, 8.1, 8.2, 8.4_

- [x] 2.5 markup の入力を検証する
  - markup と mask が同時に指定されたらエラーにする
  - markup が gpt-image-2 で指定された場合は「2.5 系専用」、フラグが無効な場合は「Azure では現在利用できない」というエラーにする
  - markup のファイルが存在すること、PNG であること、50MB 以下であることを確認し、違反したら原因を含むエラーにする
  - 先頭の入力画像と markup の寸法を読み、一致しなければ両方の寸法を含むエラーにする。どちらかの寸法が読めない場合は、確認を省いたことを警告して続行する
  - 完了条件: 単体テストで、排他、モデル非対応、ファイルの不備、寸法の不一致、寸法が読めない場合の警告を確認できる
  - _Depends: 2.1_
  - _Requirements: 7.3, 7.4, 7.5, 7.6_

- [x] 2.6 (P) URL の組み立てと、検証を通さない送信処理を公開する
  - URL の組み立てを公開し、deployments 形式（従来の URL）と v1 形式（`/openai/v1/images/...`）を API 形式で切り替える
  - 検証を通さずにリクエストを送り、HTTP のステータスにかかわらず結果（ステータスと本文）を返す公開の送信処理を用意する。通信エラーとタイムアウトだけを例外にする。v1 形式ではリクエストにデプロイ名を `model` として加える
  - 既存の生成・編集の処理を、この送信処理の上に作り直す（リトライ・エラーの分類・Base64 のデコードは従来どおり）
  - 完了条件: 単体テストで、エラーのステータスでも結果が返ること、v1 形式の URL と `model` の付与を確認できる。既存の送信処理のテストがすべて成功する
  - _Boundary: client_
  - _Requirements: 9.1, 9.5, 11.2_

- [x] 2.7 新しいパラメータとモデル別のタイムアウトをリクエストに反映する
  - complexity は値があるときだけリクエストに含める
  - 圧縮率は、出力形式がモデルの「圧縮に対応する出力形式」に含まれるときだけ送る
  - 編集で markup が指定されたら、`markup` という名前の PNG のファイル部品として送り、mask の部品は含めない
  - タイムアウトが指定されていなければ、対応表のモデル別の値（gpt-image-2 は従来の 120 秒・180 秒、2.5 系は 300 秒）を使う
  - 400 エラーの文言に、モデル種別とデプロイの対応を確認するよう促す一文を加える
  - 完了条件: 単体テストで、2.5 系のリクエストに complexity と markup の部品が入ること、gpt-image-2 では新しいパラメータが入らないこと、モデル別のタイムアウトが使われることを確認できる
  - _Requirements: 6.2, 6.3, 7.2, 8.2, 10.1, 10.2, 10.3, 11.2_

## 3. 統合: CLI への組み込み

- [x] 3.1 画像生成の CLI でモデル種別と complexity を指定できるようにする
  - `--model`（環境変数 `GPT_IMAGE_MODEL`、既定 gpt-image-2）と `--complexity`（環境変数 `GPT_IMAGE_COMPLEXITY`、既定は未指定）を追加し、「CLI 引数 > 環境変数 > 組み込み既定」の順で決める
  - 受け付けないモデル種別は、CLI 引数・環境変数のどちらから来た値でも、受け付けるモデル種別の一覧と値の出どころを示して引数エラーにする
  - quality・format・background の選択肢の制限を引数解析から外し、検証に任せる。ヘルプに使える値を書く
  - 既定モデルのときは設定を従来どおり引数なしで読み込み、それ以外のときはモデル種別を渡して読み込む。認証の解決には設定のトークンのスコープを渡す
  - quality の既定は high のままにし、デプロイ名は CLI 引数で受け取らない
  - 完了条件: CLI のテストで、優先順位、未知のモデル種別のエラー、2.5 系での xhigh の受け付け、既定モデルで設定の読み込みが引数なしで呼ばれることを確認できる。既存の生成 CLI のテストがすべて成功する
  - _Requirements: 1.2, 1.3, 2.5, 3.4, 6.1, 11.1, 11.3_

- [x] 3.2 画像編集の CLI でモデル種別・complexity・markup を指定できるようにする
  - 3.1 と同じ `--model` / `--complexity` の追加、選択肢の制限の除去、設定の読み込み方、スコープの受け渡しを行う
  - `--markup`（透過 PNG のパスを 1 つ。環境変数はなし）を追加し、編集のパラメータに渡す
  - 完了条件: CLI のテストで、`--markup` を指定した編集が markup の部品つきで送られ、`--markup` と `--mask` の併用が非ゼロで終了することを確認できる。既存の編集 CLI のテストがすべて成功する
  - _Requirements: 1.2, 1.3, 2.5, 3.4, 6.1, 7.1, 7.2, 7.3, 11.1, 11.3_

- [x] 3.3 2.5 系の一連の流れと後方互換を統合テストで確認する
  - CLI から実際の送信処理までを偽の HTTP で動かし、Flare に xhigh・opaque・complexity を指定したときのリクエスト本文・URL・タイムアウト（300 秒）を確認する
  - v1 形式での URL と `model` の付与、モデル種別ごとのデプロイ名の環境変数が URL に反映されることを確認する
  - 既定の設定（モデル種別の指定なし）で、リクエストの内容・出力・終了コードが従来と同じであることを確認する
  - 完了条件: 追加した統合テストと、既存の 118 件のテストがすべて成功する
  - _Requirements: 2.2, 6.2, 9.5, 10.1, 11.1, 11.2, 11.3, 11.4_
